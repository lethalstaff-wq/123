# SPEC — система авто-залива трафика на игровой SaaS

Документ-ТЗ. Читается сверху вниз. Предназначен для LLM-агента или разработчика,
который собирает, дополняет и эксплуатирует систему из этого репозитория.

Правило номер один: **стратегия живёт в `data/*.json`, а не в коде.** Любое
утверждение вида «в Саудовской Аравии лучше постить в 22:00» — это строка в JSON
с указанием источника, а не `if geo == "sa"` в питоне.

---

## 1. Что система делает

Вход: библиотека игровых клипов + банк форматов и хуков + гео-профили.
Выход: поток уникальных вертикальных видео, разложенный по сетке каналов
(TikTok / YouTube Shorts / Instagram Reels) по нескольким гео, с посчитанной
атрибуцией «канал → клик → подписка».

Чего система НЕ делает и не должна пытаться:
* не выдаёт себя за человека в местах, где это запрещено правилами площадки;
* не обходит антифрод и не автоматизирует то, что площадка автоматизировать не даёт
  (см. §4 — там объяснено, почему масштаб берётся иначе);
* не обещает клиенту результат, который нельзя измерить (см. §2).

## 2. Продукт и границы обещаний

Продукт: подписка на пакет твиков/утилиту для оптимизации Windows под игры.
Сопутствующие товары: мини-ПК, ноутбуки, кастомные коврики.

Три жёстких границы, которые задаются в `data/offers.json` и проверяются при
генерации подписей:

1. **Никаких обещаний конкретного прироста «на любом ПК».** Прирост зависит от
   конфигурации. Формулировка-ориентир: «стабильнее кадр и меньше фризов на том же
   железе». Числа в контенте допустимы только как «измерено на такой-то системе».
2. **Ничего, что трогает игровые файлы или античит.** EAC/Vanguard/VAC/BattlEye —
   зона, где ошибка означает бан клиента и конец проекта. Требования к продукту и
   дисклеймер — в `docs/06-risks-compliance.md` (раздел заполняется агентом
   `anticheat_safety`). Правило по умолчанию: продукт меняет настройки ОС и игры
   штатными средствами, не внедряется в процесс игры, не ставит kernel-драйверы.
3. **Технически грамотная аудитория проверяет.** Контент, который обещает
   невозможное, разбирается в комментариях, и это убивает канал быстрее любого бана.
   Поэтому банк форматов содержит `myth_bust` и `snake_oil_check` — честная позиция
   здесь работает лучше, чем накрутка ожиданий.

## 3. Архитектура

```
data/*.json ──► planner ──► render (ffmpeg) ──► publisher ──► tracker ──► review
   стратегия      что/куда      уникальный        API|RELAY|KIT    метрики     решения
                  /когда        файл                               и деньги    по слотам
```

Модули (`src/`):

| Файл | Ответственность | Ключевое решение |
|---|---|---|
| `models.py` | доменные сущности | всё сериализуемо, никакого ORM |
| `store.py` | SQLite-состояние | без него нельзя соблюдать лимиты и считать деньги |
| `config.py` | загрузка данных и секретов | секреты только из окружения |
| `planner.py` | план публикаций, выбор формата/хука/ассетов, вердикты по слотам | детерминированный seed: один и тот же план воспроизводится |
| `render.py` | сборка видео, пост-киты | ось вариативности = `variant_seed` |
| `publishers/` | доставка на площадку | три режима, деградация в KIT вместо падения |
| `tracker.py` | метрики + атрибуция выручки | без атрибуции система слепая |
| `cli.py` | единая точка входа | все операции — подкомандами |

Состояние — один файл `state.db`. Он критичен: потеря = потеря истории публикаций,
лимитов и атрибуции. Бэкап обязателен (см. `ops/RUNBOOK.md`).

## 4. Модель публикации — самое важное ограничение

Наивное ожидание: «скрипт сам постит в 400 аккаунтов». Так не работает, и вот почему.

* Официальные API публикации (TikTok Content Posting API, YouTube Data API,
  Instagram Graph API) требуют, чтобы **каждый аккаунт сам выдал доступ приложению**
  через OAuth, а приложение прошло аудит. Квоты считаются на приложение/проект, а не
  на аккаунт: у YouTube загрузка стоит фиксированное число единиц квоты, и дневной
  лимит проекта упирается в единицы быстрее, чем в число каналов
  (`data/platform_limits.json → youtube.api`).
* Instagram вообще не принимает байты файла — только публичный URL видео. Значит в
  системе обязателен шаг хостинга рендеров.
* Всё остальное — неофициальная автоматизация (мобильные фермы, Selenium, приватные
  API). Она работает до первой волны зачисток и забирает аккаунты целиком, вместе с
  историей и подписчиками.

Отсюда три режима, и слот выбирает свой:

| Режим | Кто публикует | Для чего |
|---|---|---|
| `api` | система напрямую | 1-2 флагманских канала на платформу, где стоит пройти OAuth/аудит |
| `relay` | сторонний планировщик с мульти-аккаунтом | средний слой каналов; провайдер держит интеграции у себя |
| `kit` | человек или устройство аккаунта | основная масса каналов |

В режиме `kit` система делает всё, кроме нажатия кнопки: рендер, подпись, хештеги,
время, чеклист (`out/<geo>/<platform>/<slot>/<plan>.kit.json`). Факт публикации
возвращается в систему командой `record-post` — иначе метрики и атрибуция разъедутся.

**Вывод для планирования:** масштаб даёт не «более хитрый скрипт», а число слотов в
`kit`/`relay` и дисциплина в их обслуживании. Скрипт убирает 90% работы (монтаж,
тексты, расписание, учёт), но не превращает 400 аккаунтов в ноль человеко-часов.

## 5. Слой данных

| Файл | Что описывает | Кто заполняет |
|---|---|---|
| `geos.json` | гео-профили: язык, игры, сленг, цена, точка приёма, таймзона | ресерч по странам |
| `schedule.json` | окна постинга в локальном времени + пороги решений | ресерч по таймингам |
| `platform_limits.json` | лимиты, квоты, требования API | ресерч по площадкам |
| `content_bank.json` | форматы, шаблоны хуков, хештеги, CTA | ресерч по форматам + ручное расширение |
| `hooks_expanded.json` | тысячи конкретных хуков | генерируется `scripts/expand_hooks.py` |
| `channels.json` | 20 слотов каналов на платформу | этот репозиторий |
| `offers.json` | цены по тирам регионов, разрешённые и запрещённые формулировки | ресерч по ценам |
| `assets.json` | индекс клипов | генерируется `cli assets scan` |

Правило источников: любая цифра в этих файлах, взятая не из документации площадки,
несёт рядом источник и уровень доверия (см. `_sources` в `platform_limits.json`).
Цифра без источника — гипотеза, и её нельзя закладывать в решения о деньгах.

## 6. Уникализация контента

Один файл, залитый в 20 аккаунтов, — это (а) дублирующий контент по правилам площадок,
(б) взаимная каннибализация показов. Поэтому уникальность обеспечивается на рендере,
а не «заменой обложки».

Оси, которыми управляет `variant_seed` (`render.py`):

* какие отрезки клипов берутся и в каком порядке;
* темп (0.94–1.10) и зум (1.00–1.12) — меняют и хеш, и визуальную динамику;
* цветокоррекция (5 вариантов);
* шрифт/размер/позиция/стиль плашки хука (4 позиции × 4 размера × 4 стиля);
* длительность (формат задаёт вилку);
* музыкальная дорожка и её громкость;
* сам текст хука — из `hooks_expanded.json` (тысячи вариантов на язык).

Проверка: `store.checksum_seen()` ловит побайтово идентичные рендеры и пишет
предупреждение. Если оно появляется — мало ассетов или мало хуков, а не «сойдёт».

## 7. Гео: что реально управляет выдачей

<!-- RESEARCH: раздел уточняется агентом geo_targeting_truth (прогон wr5lxqxv5) -->

Рабочая гипотеза, на которой построен код (порядок по силе влияния):

1. **Язык текста на экране и подписи** — самый сильный управляемый фактор.
2. **Язык озвучки/субтитров** и выбранное аудио.
3. **Поведение первых зрителей** (кому алгоритм показал и как они отреагировали).
4. **Язык метаданных** (заголовок, описание, теги).
5. **Страна аккаунта** (настройка профиля/канала).
6. **IP загрузки** — влияет на первичный тест, но переоценён практиками.
7. **Город внутри страны** — влияния на распределение контента не подтверждено.
   Город имеет значение только как качество и доступность IP-пула и как таймзона.

Практический вывод, заложенный в `geos.json`: `needs_local_ip` по умолчанию `false`.
Прежде чем платить за прокси, ставится эксперимент из §11: один и тот же формат на
двух языках. Если арабоязычный вариант даёт целевое гео, а англоязычный нет — дело в
языке, и прокси ничего не добавит.

## 8. Сетка каналов

20 слотов на платформу на гео (`channels.json`), разведённых по осям: игра → формат →
под-ниша → персона. Ни один слот не повторяет другой.

Структура 20 слотов: 12 игровых (по тайтлу), 4 «железных» (ноутбуки, слабое железо,
мини-ПК, периферия), 4 «мета» (разоблачение мифов, настройки про, диагностика фризов,
satisfying-бенчмарки).

Что обязательно разное между слотами: тема, ник (не по шаблону с цифрами), bio,
набор форматов, темп постинга, целевая игра. Что общее: точка приёма трафика и
качество продукта.

`attribution_token` слота (`us` + `tt` + `01` → `ustt01`) — это метка, которая
уезжает в ссылку/инвайт/промокод. Без неё нельзя ответить, какой из 360 каналов
принёс деньги.

## 9. Тайминги

`schedule.json → by_geo[geo][platform]` — окна в **локальном** времени гео;
`planner` переводит их в UTC по `geos.json → timezone` и добавляет джиттер
(по умолчанию ±25-30 минут). Джиттер обязателен: 20 аккаунтов, публикующих в
одну минуту, — самый заметный машинный признак.

Честная оценка: время постинга — фактор третьего порядка. Разница между плохим и
хорошим хуком больше, чем между плохим и хорошим временем. Не оптимизировать
расписание, пока не оптимизирован хук.

## 10. Воронка и атрибуция

Путь: видео → профиль → ссылка в bio → точка приёма → оплата → выдача доступа.

Точка приёма выбирается по гео (`offers.json → funnel_entry`): Discord для
англоязычных и большинства рынков, Telegram для СНГ и части MENA, сайт для DE/JP/KR,
WhatsApp там, где он основной мессенджер.

Атрибуция без бюджета на трекеры:
* уникальный инвайт Discord или `?ref=<token>` на каждый слот;
* промокод на слот (он же служит скидкой — двойная польза);
* `tracker.ingest_conversion()` принимает вебхук платёжки и раскладывает выручку по
  токенам; всё без метки падает в бакет `unattributed` — его размер показывает,
  сколько трафика вы не считаете.

## 11. Метрики и решения

Пороги — в `schedule.json → decision_thresholds`, вердикты считает
`planner.review_slots()`: `scale` / `keep` / `kill` / `too_early`.

Обязательные метрики:
* просмотры и медиана просмотров по слоту;
* **доля просмотров из целевого гео** (`cli report-geo`) — если ниже порога, проблема
  в языке и контенте;
* CTR в профиль и клики по ссылке;
* конверсия в оплату по `attribution_token`.

Эксперимент для выбора гео (2-3 недели, до траты денег на инфраструктуру):
берутся 2-3 гео × 2 канала × один и тот же набор форматов; переменная одна — язык
контента. Сравниваются медианные просмотры, доля целевого гео и клики. Гео, где
целевая доля ниже порога при нормальных просмотрах, не «требует прокси» — оно
требует другого языка или другого формата.

## 12. Риски

<!-- RESEARCH: раздел дополняется агентами network_architecture, bought_accounts, payments_stack, accounts_grey -->

Что известно уже сейчас и заложено в систему:

* **Покупные «новореги»** — нарушение правил всех трёх площадок и типичная причина
  ранней смерти сетки: массово созданные аккаунты часто уже помечены. Система
  поддерживает состояние аккаунта (`warming/active/limited/banned`) и снижает темп
  на прогреве, но не компенсирует плохой источник аккаунтов.
* **Одинаковый контент** — прямое попадание под политики о неоригинальном контенте.
  Противоядие — §6, а не «поменять первый кадр».
* **Продажа игровых аккаунтов** (обсуждалась как одна из товарных категорий) —
  запрещена правилами Epic/Riot/Valve и политиками PayPal/Stripe. Риск не в блокировке
  соцсетей, а в потере платёжки, через которую идут деньги за подписку. Держать
  отдельно от основного бренда, платёжки и Discord — либо не держать вовсе.
* **Чарджбеки** от молодой аудитории — причина заморозки платёжных аккаунтов.
  Нужны внятные ToS, политика возврата и логи выдачи доступа.
* **Потеря `state.db`** — потеря атрибуции и лимитов. Бэкап ежедневно.

## 13. Порядок сборки

Для агента, который продолжает работу, по шагам:

1. `python -m src.cli doctor` — окружение и целостность данных.
2. Заменить `data/geos.json` полными профилями из ресерча (36 стран), выставить
   `priority` по итоговому рейтингу.
3. Обновить `data/platform_limits.json` и `data/schedule.json` подтверждёнными
   цифрами; заменить `RESEARCH_PENDING` на источник и дату.
4. Расширить `content_bank.json` форматами из ресерча, перегенерировать
   `hooks_expanded.json`.
5. Подключить `hooks_expanded.json` в `planner.pick_hook()` (сейчас читается
   `content_bank.hooks`; нужен переключатель на расширенный банк).
6. Реализовать хостинг рендеров (нужен Instagram) и передачу `public_video_url`.
7. Дописать `publishers/relay.py` под выбранного провайдера из ресерча.
8. Настроить приём вебхуков платёжки в `tracker.ingest_conversion`.
9. Наполнить `assets/` реальными клипами, `cli assets scan`.
10. Прогнать цикл: `plan → render → publish → record-post → import-metrics → review`.

Definition of Done для системы:
* `doctor` без ошибок; `plan → render` даёт файлы с уникальными хешами;
* `publish` в KIT-режиме отдаёт киты, `record-post` возвращает факт публикации;
* `review` показывает вердикты по слотам на реальных метриках;
* хотя бы одна конверсия привязана к `attribution_token`.

## 14. Антипаттерны

* Хардкод стратегии в коде вместо `data/*.json`.
* Публикация одного файла в несколько аккаунтов.
* Одно время постинга для всех аккаунтов гео.
* Масштабирование до того, как посчитана доля целевого гео и конверсия.
* Покупка прокси и аккаунтов раньше, чем проверен хук и язык.
* Цифры в контенте, которые нельзя подтвердить замером.
* Смешивание серых товарных категорий с платёжкой основного продукта.
